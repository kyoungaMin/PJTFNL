### 1. 로그인 세션 관리 개선

#### 문제
- 새로고침 시 세션 유지는 OK였으나, 탭 닫고 다시 localhost 접속 시 로그인 없이 메인으로 바로 진입되는 버그 발생
- Supabase 세션이 `localStorage`에 저장되어 탭 종료 후에도 유지되는 것이 원인

#### 해결: `sessionStorage` 플래그 방식 도입

| 동작 | 이전 | 수정 후 |
|------|------|---------|
| 새로고침(F5) | 세션 유지 ✅ | 세션 유지 ✅ |
| 탭 닫고 재접속 | 바로 메인 진입 ❌ | 로그인 화면 ✅ |
| 로그아웃 후 재접속 | 로그인 화면 ✅ | 로그인 화면 ✅ |

**수정 파일:**
- `forecastai/src/app/page.tsx`: 세션 복원 시 `sessionStorage.getItem('session_active')` 플래그 체크. 없으면 복원 건너뜀
- `forecastai/src/components/pages/Login.tsx`: 로그인 성공 시 `sessionStorage.setItem('session_active', '1')` 저장
- `forecastai/src/components/layout/index.tsx`: 로그아웃 시 `sessionStorage.removeItem('session_active')` 제거

### 6. 이메일/사용자 정보 하드코딩 제거 — DB 동적 연동

#### 문제
- 관리자 페이지 유저 테이블에서 이메일이 이전 버전으로 표시됨
- 헤더 오른쪽 유저 드롭다운 이메일도 이전 버전
- 로그인 화면 간편 로그인 버튼이 `data.ts` 하드코딩 이메일로 고정되어 있어, 관리자가 계정을 추가해도 반영 안 됨

#### 원인
- `user_profile.email` 컬럼이 Supabase Auth 실제 이메일과 동기화 안 됨
- 로그인 실패 시 `LOGIN_ACCOUNTS` 하드코딩 데이터를 fallback으로 사용
- 간편 로그인 버튼이 `data.ts`의 `LOGIN_ACCOUNTS` 고정 배열을 렌더링

#### 해결

**① `/api/me` — Auth 이메일 우선 반환**
```ts
// Supabase Auth 이메일을 항상 우선 사용
return NextResponse.json({
  ...profile,
  email: userData.user.email ?? profile.email ?? '',
})
```

**② `/api/admin/users` — Auth 이메일로 override**
```ts
const { data: authUsers } = await supabase.auth.admin.listUsers({ perPage: 1000 })
const authEmailMap = new Map(authUsers?.users?.map(u => [u.id, u.email]))
const merged = data.map(u => ({ ...u, email: authEmailMap.get(u.id) ?? u.email ?? '' }))
```

**③ `/api/quick-accounts` (신규 API)**
- 인증 없이 접근 가능 (로그인 화면용)
- `auth.admin.listUsers()`로 실제 이메일 + `user_profile` 이름/역할 합쳐서 반환
- 관리자가 Admin 페이지에서 계정 추가 시 자동으로 간편 로그인 버튼에 반영

**④ `Login.tsx` 하드코딩 제거**
- `LOGIN_ACCOUNTS` import 및 fallback 완전 제거
- 간편 로그인 버튼: `/api/quick-accounts` API 동적 호출 (`useEffect`)
- DB 조회 실패 시 버튼 자체가 숨겨짐 (오류 없음)

### 8. 대시보드 실데이터 연결 구조 정리

대시보드 전 구역이 DB 실데이터와 연결되어 있음. 핵심 구조 요약.

#### 데이터 흐름

```
Supabase DB → /api/dashboard → Dashboard.tsx (차트·KPI 렌더)
```

#### 구역별 연결 테이블 / RPC

| 구역 | 소스 | 비고 |
|------|------|------|
| 수주량 실적선 (최근 26주) | `get_order_weekly_summary` RPC | M/DD 라벨, 3개마다 1개 표시 |
| 수주량 예측 밴드 P10/P50/P90 | `get_forecast_summary` RPC → `forecast_result` | h=7/14/21/28/56/91, 6호라이즌 |
| 재고 커버리지 KPI | `get_inventory_coverage` RPC | `inventory` + `daily_order` 집계 |
| 구매 발주 KPI | `purchase_order` | status R/P 미처리 건수 |
| 위험 도넛 | `get_risk_grade_summary` RPC → `risk_score` | A/B/C/D 등급 |
| AI 생산 권고 Top3 | `action_queue` + `product_master` 조인 | pending/critical/high |
| AI 인사이트 요약 | GPT-4o-mini (DB 집계 후 분석) | 6시간 서버 캐시 |
| 헤더 알림 | `action_queue` + `risk_score` + `purchase_order` | 벨 클릭 시 lazy fetch |

#### Supabase limit=1000 회피 패턴

대용량 테이블(`daily_order` 등)은 REST 직접 조회 시 최대 1000건 제한으로 집계 오류 발생.
→ **DB 집계 RPC 함수**로 서버 사이드 집계 후 결과만 반환:
- `get_order_weekly_summary(p_from_date)` — 최근 26주 주간 수주량
- `get_order_monthly_summary(p_from_date)` — 최근 3개월 월간 수주량 (AI 인사이트용)
- `get_inventory_coverage(p_from_date, p_to_date)` — 재고 커버리지 일수
- `get_forecast_summary(p_date)` — 예측 밴드 P10/P50/P90
- `get_risk_grade_summary(p_date)` — 위험 등급별 건수

#### 시스템 기준날짜 고정

실데이터 최신일이 `2026-02-28`이므로 `SYSTEM_BASE_DATE = '2026-02-28'`으로 고정.
실 서비스 전환 시 해당 상수를 `new Date()`로 교체하면 됨.
→ 적용 파일: `api/dashboard/route.ts`, `api/ai-insights/route.ts`

### 9. AI 인사이트 동작 방식

대시보드 하단 "AI 인사이트 요약" 카드는 **GPT-4o-mini**가 DB 실데이터를 분석해 생성.

#### 동작 흐름

```
GET /api/ai-insights
  → 캐시 유효(6시간 이내)? → 캐시 반환 (GPT 호출 없음, 비용 절감)
  → 캐시 만료? → DB 실데이터 수집 → GPT 호출 → 결과 캐시 저장 후 반환
```

#### GPT에 전달하는 실데이터

| 항목 | 소스 | 예시 |
|------|------|------|
| 이번 달 누적 수주량 | `get_order_monthly_summary` | 45,230 EA |
| 전월 수주량 | 동일 | 41,800 EA |
| 전전월 대비 전월 증감률 | 계산값 | +8.2% |
| 재고 커버리지 | `get_inventory_coverage` | 18일 (목표 21일) |
| 미처리 구매 발주 건수 | `purchase_order` | 127건 |
| 현재 USD/KRW 환율 | `exchange_rate` | 1,432원 |
| 최근 30일 환율 변동률 | 계산값 | +1.3% |

#### GPT 출력 규칙

- 5개 인사이트, JSON 배열 형식으로만 반환
- `color`: blue / red / amber / green / purple (중요도·긴급도에 따라 선택)
- `text`: 한국어 1~2문장, 구체적 수치 포함, 생산계획팀이 바로 활용 가능한 내용
- `temperature: 0.4` → 낮게 설정해 일관성 있는 분석 유지
- GPT 실패 시 amber 색상 에러 메시지 fallback 반환 (UI 빈 화면 방지)
